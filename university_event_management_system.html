Arxitektura "SOLID prinsiplərinə uyğun JS Tədbir idarəetmə class-ı necə qurular?" Single Responsibility prinsipinə uyğun olaraq Event, User, və Registration servislərini ayırmağı təklif etdi. Monolit koda əvəz modular `EventManager` və `ValidationService` sinifləri yaradıldı. SOLID (SRP/OCP)
DB Layihələndirmə "İştirakçı limiti dolduqda avtomatik Gözləmə siyahısı (Waitlist) SQL strukturu." Waitlist cədvəlində `created_at` sırası ilə növbə yaratmağı və UNIQUE constraint tətbiq etməyi tövsiyə etdi. `Waitlist` relyasiyası əlavə olundu və qeydiyyat ləğvində FIFO avto-promosiya kodu yazıldı. Database Normalization
Təhlükəsizlik "Frontend qeydiyyatında təkrar registrasiyanın və tarix xətalarının qarşısını almaq." XSS-in qarşısını almaq üçün input sanitization və JS validations təqdim olundu. Tarix yoxlama helper-i və unikal istifadəçi-tədbir cütü daxili map ilə bloklandı. Input Validation & Sanitization
Testləşdirmə "Tədbir limitinin aşılması halları üçün hansı edge-case unit testləri yazılmalıdır?" Eyni vaxtda olan istək simulyasiyası və keçmiş tarixlərə qeydiyyat bloklama ssenariləri. 5 formal test ssenarisi formalaşdırıldı və avtomatlaşdırılmış runner tərtib edildi. Boundary Value Analysis

Texniki Arxitektura və Verilənlər Bazası Strukturu

Sistemin daxili iş prinsipi, relyasiyalar və təhlükəsizlik prinsipləri

1. Events (Tədbirlər)
  • PK id: INTEGER
  • title: VARCHAR(255)
  • category_id: FK(Categories)
  • date_time: DATETIME
  • location: VARCHAR(255)
  • max_capacity: INT
  • description: TEXT
2. Registrations (Qeydiyyatlar)
  • PK id: INTEGER
  • event_id: FK(Events)
  • user_id: FK(Users)
  • registration_date: DATETIME
  • attended: BOOLEAN
  • UNIQUE(event_id, user_id)
3. Waitlist (Gözləmə Siyahısı)
  • PK id: INTEGER
  • event_id: FK(Events)
  • user_id: FK(Users)
  • added_at: DATETIME
  • status: ENUM('WAITING','PROMOTED')
